title: Build a plugin
description: Scaffold a new Corsair plugin with the generator, then let Claude Code fill in the implementation.

<Tip>
**Use Claude Code to build your plugin.** Run the steps below in your terminal, then paste the prompt from the guide into Claude Code. It will fill in the real API calls for you.
</Tip>

The fastest way to build a custom plugin is to use the built-in generator. It scaffolds the full directory structure, wires up types, and registers your plugin. Then you (or Claude Code) fill in the real API calls.

<Steps>

<Step title="Fork or clone the Corsair repo">
Plugins live inside the monorepo alongside the core library.

```bash
git clone https://github.com/corsairdev/corsair.git
cd corsair
pnpm install
```

</Step>

<Step title="Run the plugin generator">
Pass your plugin name in **PascalCase**, for example `Stripe`, `GoogleCalendar`, or `HubSpot`.

```bash
pnpm run generate:plugin <PluginName>
```

For example:

```bash
pnpm run generate:plugin Stripe
```

This creates `packages/stripe/` with the full plugin structure:

```
packages/stripe/
├── index.ts
├── client.ts
├── error-handlers.ts
├── package.json
├── tsconfig.json
├── tsup.config.ts
├── endpoints/
│   ├── index.ts
│   ├── types.ts
│   └── example.ts
├── webhooks/
│   ├── index.ts
│   ├── types.ts
│   └── example.ts
└── schema/
    ├── index.ts
    └── database.ts
```

It also automatically registers your plugin in `packages/corsair/core/constants.ts`.

</Step>

<Step title="Choose your auth type">
Open `packages/<yourplugin>/index.ts` and update the auth type to match the API you're integrating with.

**API key** (most REST APIs):

```ts
authType?: PickAuth<'api_key'>;
```

**OAuth 2** (Google, GitHub, etc.):

```ts
authType?: PickAuth<'oauth_2'>;
```

Also update the `defaultAuthType` constant and `authConfig` to match:

```ts
const defaultAuthType: AuthTypes = 'api_key'; // or 'oauth_2'

export const stripeAuthConfig = {
    api_key: {
        account: ['one'] as const,
    },
} as const satisfies PluginAuthConfig;
```

</Step>

<Step title="Let Claude Code implement it">
Point Claude Code at the API docs for your integration and let it do the heavy lifting.

Open Claude Code in the repo root and give it a prompt like:

```
I've generated a Corsair plugin scaffold at packages/stripe/.
Please implement it using the Stripe API docs at https://docs.stripe.com/api.

- Update client.ts with the correct base URL and auth headers (Bearer token)
- Replace the example endpoint with real Stripe endpoints (e.g. list customers, get invoice)
- Update the schema/database.ts with relevant entity shapes
- Remove the example webhook and add real Stripe webhook event types
```

Claude Code can read the scaffold, understand the patterns from existing plugins (e.g. `packages/github/`), and produce a working starting point.

</Step>

<Step title="Typecheck and build">
```bash
cd packages/<yourplugin>
pnpm typecheck
pnpm build
```

Fix any type errors, then register the plugin in your app the same way as any other Corsair plugin:

```ts src/server/corsair.ts
import { stripe } from '@corsair-dev/stripe';

export const corsair = createCorsair({
    plugins: [stripe({ key: process.env.STRIPE_API_KEY })],
    database: db,
    kek: process.env.CORSAIR_KEK!,
});
```

</Step>

<Step title="Test your plugin">
The repo includes a ready-made testing sandbox at `demo/testing/`. Add your plugin there and run scripts against it without setting up a new project.

**1. Add your plugin as a workspace dependency in `demo/testing/package.json`:**

```json demo/testing/package.json
{
  "dependencies": {
    "@corsair-dev/stripe": "workspace:*"
  }
}
```

Then run `pnpm install` from the repo root to link it.

**2. Register your plugin in the test corsair instance:**

```ts demo/testing/src/server/corsair.ts
import { stripe } from '@corsair-dev/stripe';

export const corsair = createCorsair({
    plugins: [
        // ... existing plugins
        stripe({ key: process.env.STRIPE_API_KEY }),
    ],
    database: sqlite,
    kek: process.env.CORSAIR_KEK!,
});
```

**3. Write your test in `demo/testing/src/scripts/test-script.ts`:**

```ts demo/testing/src/scripts/test-script.ts
import { corsair } from '@/server/corsair';
import 'dotenv/config';

const main = async () => {
    const customer = await corsair.stripe.api.customers.get({ id: 'cus_123' });
    console.log(customer);
};

main();
```

**4. Run the script:**

```bash
cd demo/testing
pnpm run test
```

<Info>
**Build watch required**
In a separate terminal, run the build watcher in your plugin package so changes are picked up immediately:

```bash
cd packages/stripe
pnpm run build --watch
```

Without this, the test sandbox will be running stale compiled output.
</Info>

</Step>

</Steps>


## Let search read your plugin live (optional)

If an endpoint searches or lists records, add a `search` block to its `endpointMeta` entry. It tells Corsair how to turn what a question makes certain (people, a date window, kinds, states, ids, topic words) into that endpoint's arguments, so a search can ask your app directly. The block is plain JSON: no functions. Without it the plugin is simply not searched live.

```ts
'messages.list': {
  riskLevel: 'read',
  search: {
    kinds: ['messages'],              // entities the rows are, as in your schema
    rows: 'messages',                 // path to the row list in the result ('' if the result is the list)
    id: 'id',                         // field in each row that holds its id
    open: { op: 'messages.get', idArg: 'id' }, // optional: read one result by id
    limit: { arg: 'maxResults', default: 25, max: 100 },
    fixed: { sort: 'timestamp' },     // optional: args sent every time
    hints: {
      topic: { arg: 'q', text: '{v}' },
      people: { arg: 'q', text: ['from:{v}', 'to:{v}'], join: 'or' },
      after: { arg: 'q', text: 'after:{v}', format: 'epoch' },
      before: { arg: 'q', text: 'before:{v}', format: 'epoch' },
      states: { map: { unread: { arg: 'q', text: 'is:unread' } } },
    },
  },
},
```

Each hint (`topic`, `people`, `places`, `ids`, `after`, `before`, `window`, `kinds`, `states`) is optional; declare only what the provider can filter on. A part names the argument it fills (`arg` is a dot path such as `filter.updatedAt.gte`) and gives exactly one of:

- `text`: query-string apps. Terms are appended to the string at `arg`, `{v}` is the value, and a value with spaces or operator characters is quoted. `join: 'or'` writes several values as `(a OR b)`; the default repeats the term.
- `list`: structured apps. Templates are pushed onto the array at `arg`, once per value.
- `set`: structured apps. One value is set at `arg`; with no `{v}` it is a constant.

Dates arrive as ISO instants. `format` is `iso`, `epoch` (seconds), `YYYY-MM-DD` or `YYYY/MM/DD`; day formats are written in the caller's time zone, and `shiftDays` moves them for a provider whose bound excludes its own day. Set `max` or `cap` where the provider cannot take more (a query length limit, two values that contradict each other): a hint past its limit is left out, so the search widens instead of guessing.

Check each operator against the provider's search documentation. `pnpm test` checks the rest: every `arg` exists in the endpoint's input schema, the compiled arguments pass that schema, and `rows` and `id` exist in its output.

## Tips

- **Look at existing plugins** for reference. `packages/github/` and `packages/resend/` are good examples at different complexity levels.
- **Auth headers** go in `client.ts` inside the `HEADERS` config object. Most APIs use `Authorization: Bearer <key>` or `Authorization: <key>`.
- **Webhook signature verification**: update the `TODO` in `webhooks/types.ts` with the HMAC logic for your provider. Check it against the raw body (`request.rawBody`), not re-serialized JSON. When a check fails, return `{ success: false, error }` instead of throwing: `processWebhook` reports it as a refusal (400), while a thrown error becomes a 500 that the sender retries.
- **Errors from `client.ts`**: let core's `ApiError` through unchanged, as the scaffold does. Its `status` and `retryAfter` are what error handlers match and what core reads to refresh an OAuth token after a 401. Wrapping it in a new error hides both.
- **Rate limits**: core's `request()` already retries a 429 three times and honors `Retry-After`. Keep the scaffold's `RATE_LIMIT_ERROR` handler at `maxRetries: 0` unless the endpoint needs more, or the attempts multiply.
- **Mark reads as reads**: give each endpoint that only reads `riskLevel: 'read'` in the plugin's endpoint meta (the scaffold's `example.get` shows it). For OAuth plugins, core refreshes the token once and repeats a read that comes back 401. It leaves writes alone, because repeating one could send a request twice. If your endpoints already decide which 401s deserve a refresh, set `refreshOnUnauthorized: false` on the plugin.
- **Database entities**: define Zod schemas in `schema/database.ts` for any data you want to cache locally. Leave `entities: {}` empty if you only need live API calls.
